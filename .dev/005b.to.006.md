# Roadmap: v0.0.5.1 → v0.0.6

## v0.0.6 - Interactive Chemistry + Stronger Graphing

v0.0.6 should focus on making two existing areas feel like complete tools instead of basic text utilities:

1. **Periodic Table → Interactive Chemistry Tool**
2. **Graphing → clearer controls + stronger plotting capabilities**

The release should reuse the existing CLI navigation/theme infrastructure and avoid creating a second, incompatible menu system. The current `display_menu()` already provides highlighted selection, arrow-key navigation, Enter-to-select, numeric shortcuts, breadcrumbs, and contextual help; the new UI layer should build on that foundation. fileciteturn13file0

## 1. Periodic Table — Convert Lookup into an Interactive Tool

### Goal

Replace the current "Periodic Table" behavior in **Chemistry** with a real interactive periodic-table experience rather than a paginated searchable table.

Today the Chemistry menu routes option 9 to `run_periodic_table_menu()`, which currently renders 20-element pages and provides command-style search/view controls. The underlying element data is loaded from `data/periodic_table.json`. fileciteturn5file0 fileciteturn6file0

### Menu Change

Change:

`CHEMISTRY → 9. Periodic Table`

into:

`CHEMISTRY → 9. Periodic Table`

but make the destination an **interactive periodic-table UI** with selectable elements instead of a standard text lookup workflow.

### Interactive Periodic Table UI

Build a reusable grid/selectable UI component for the periodic table.

#### Requirements

- Render all 118 elements in an actual periodic-table layout by period/group.
- Preserve the lanthanide and actinide rows in the conventional detached layout.
- Each element tile should show at minimum:
  - Atomic number
  - Symbol
  - Element name (when terminal width allows)
- Highlight the currently selected element.
- Navigate element-to-element with arrow keys.
- `Enter` opens the selected element's detail view.
- Provide a keyboard-search shortcut for jumping directly to an element by:
  - symbol
  - name
  - atomic number
- Provide an obvious way to return to the previous Chemistry menu.
- Keep the UI usable on narrower terminals; provide a compact fallback representation when the full grid cannot fit.

### Element Detail View

Selecting an element should open a dedicated detail screen rather than printing only four values.

#### Element Information Database

Expand the periodic-table data model beyond the current `name`, `number`, `mass`, and `category` fields. fileciteturn10file0

Target fields should include, where available and useful:

- Name
- Symbol
- Atomic number
- Atomic mass
- Category / classification
- Period
- Group
- Block (`s`, `p`, `d`, `f`)
- State at room temperature
- Electron configuration
- Valence-electron information where appropriate
- Electronegativity where available
- Common oxidation states
- Phase / physical state metadata

Do not make the UI dependent on every field being populated. Missing optional values should display as `N/A` rather than breaking rendering.

### Element Properties Lookup

The detail view should make the periodic table useful as a reference tool, not just a selector.

Support:

- Full element-property display
- Compact summary mode
- Search/jump by property-supported identifiers
- Consistent numeric formatting
- Reuse of the same element lookup logic from molar-mass/reference features to avoid duplicated matching code

### Electron Configuration Visualization

Add a dedicated **Electron Configuration** section to the element detail view.

#### Minimum functionality

- Show the full electron configuration.
- Show noble-gas shorthand when useful.
- Visualize orbital/subshell occupancy in a terminal-friendly format.
- Clearly distinguish:
  - energy level (`n`)
  - subshell (`s/p/d/f`)
  - electron count
- Provide a simplified shell-count summary for quick studying.

The implementation should use element data plus a centralized configuration engine/data source, with known ground-state exceptions handled explicitly rather than silently assuming a simplistic Aufbau sequence for every element.

### Global UI System

Use the periodic-table work to establish a reusable **interactive selector/grid UI primitive** that can later be used throughout Workstation CLI.

Possible reusable capabilities:

- Arrow-key navigation
- Selected/highlighted item state
- Enter to open/select
- Escape / `q` to go back
- Search/jump action
- Responsive compact mode
- Shared header/footer/help presentation

Do not make the periodic table a one-off rendering hack. Separate:

1. **data/model**
2. **selection/navigation state**
3. **terminal rendering**
4. **detail view**

so the same UI system can eventually support other grid/list-based tools.

### Integration / Refactor

The existing Chemistry Reference module currently contains both `_lookup_element()` and `run_periodic_table_menu()`. Refactor these so there is one canonical element-query/detail implementation and the interactive table calls into it. fileciteturn6file0

Avoid maintaining three separate copies of element matching/detail formatting.

### Periodic Table Acceptance Criteria

- [ ] All 118 elements can be reached from the interactive table.
- [ ] Arrow-key navigation works correctly across the grid and detached f-block rows.
- [ ] Selecting an element opens a full detail view.
- [ ] Name, symbol, and atomic-number lookup all jump to the correct element.
- [ ] Electron configuration is displayed correctly, including known exceptions.
- [ ] Existing chemistry calculations that depend on `load_periodic_table()` continue to work.
- [ ] Narrow terminals do not produce unusable overflow.
- [ ] The interactive selector is implemented as reusable infrastructure rather than table-specific code.
- [ ] Existing Periodic Table lookup behavior is replaced cleanly without breaking Chemistry navigation.

## 2. Graphing — Improve Controls and Plotting Capabilities

### Goal

Make the Graphing Tool substantially easier to understand and more useful while preserving its current offline ASCII/Unicode architecture.

The current graphing system already supports custom `f(x)` expressions, preset functions, customizable domain ranges, and terminal rendering. fileciteturn9file0 fileciteturn11file0

### 2.1 Clarify X `min` and `max`

The current custom plotter asks:

- `Enter x min [-10.0]`
- `Enter x max [10.0]`

The interface should make it immediately obvious that these values define the **horizontal domain shown on the graph**.

Replace ambiguous prompts with wording such as:

`X-axis minimum (left edge) [-10.0]:`

`X-axis maximum (right edge) [10.0]:`

Add a brief inline hint:

`Controls the visible X range from left → right.`

Do the same conceptually anywhere a graph range is configured.

### 2.2 Separate Domain from Graph Scaling

Make the distinction explicit between:

- **X domain** — which x-values are sampled/plotted
- **Y range** — which vertical values are visible
- **Plot size** — terminal width/height

The current plotter already accepts optional `y_min`, `y_max`, width, and height, but the custom-function UI does not expose these concepts clearly. fileciteturn11file0

Add a clearer configuration flow:

`X Range`
`Y Range`
`Plot Size`

with sensible defaults and an option to use automatic Y scaling.

### 2.3 Better Graphing Menu Structure

Expand the existing Graphing menu into a more capable toolset.

Proposed structure:

- `1. Plot Custom Function`
- `2. Preset Functions`
- `3. Plot Settings`
- `4. Graph Help / Controls`
- `0. Return`

Do not force users through settings they do not need. The common path should remain fast.

### 2.4 Improved Axis / Range Readability

Improve generated plots so the terminal output communicates the selected ranges more clearly.

Add or improve:

- X-axis endpoint labels
- Y-axis endpoint labels
- Zero markers when visible
- Clearer axis intersection
- Domain/range summary above or below the graph
- Consistent decimal formatting
- Better handling when zero is outside the visible domain
- Better handling when the curve has discontinuities or invalid regions

The current renderer draws axes when zero falls within the configured bounds and automatically derives Y values when a Y range is not supplied. Preserve that behavior while making the resulting graph easier to interpret. fileciteturn11file0

### 2.5 Plotting Robustness

Improve plotting behavior for real-world expressions:

- Handle discontinuities without drawing misleading connecting segments.
- Handle undefined values cleanly.
- Detect extreme values/outliers that flatten the rest of a plot.
- Avoid crashes from functions such as `log(x)`, `sqrt(x)`, and `1/x`.
- Validate finite numeric ranges before rendering.
- Provide useful error messages when a chosen domain is invalid for the expression.

### 2.6 Better Sampling / Resolution

Review the current fixed-width sampling approach and improve resolution handling.

Potential improvements:

- Configurable terminal plot width/height
- Sampling density based on plot width
- Optional denser sampling for steep/rapidly changing functions
- Avoid unnecessary computation when a point cannot affect the visible plot

Do not over-engineer this into a GUI plotting engine; keep the terminal-first design.

### 2.7 Multiple-Function Support

Prepare the graphing architecture for plotting more than one function on the same coordinate system.

For v0.0.6, support at least a clean internal model for multiple plotted series even if the user-facing interface initially limits the feature to a small number of functions.

Future-ready data model should separate:

- expression
- parsed function
- display label
- sampling state
- plot character/style

### 2.8 Preset Improvements

Keep the current preset library, but make presets behave like normal graph definitions so they share the same rendering/configuration pipeline.

Current presets include quadratic, cubic, sine, cosine, Gaussian, logarithmic, and reciprocal functions. fileciteturn11file0

Presets should gain:

- Clearer descriptions
- More intentional default X/Y ranges
- Reusable configuration objects
- Optional user override of the preset domain

### Graphing Acceptance Criteria

- [ ] X min/max prompts explicitly explain left/right visible X range.
- [ ] X domain, Y range, and plot size are clearly separated in the UI.
- [ ] Users can keep automatic Y scaling or specify a Y range.
- [ ] Graph labels accurately reflect the selected ranges.
- [ ] Invalid/undefined regions do not crash the tool or create misleading lines.
- [ ] Plot resolution can be adjusted without rewriting the plotting engine.
- [ ] Presets and custom functions use the same core plotting pipeline.
- [ ] Graphing code remains terminal-first and works offline.
- [ ] Multiple-function plotting is structurally supported or cleanly scaffolded for the next release.

## 3. Shared Architecture / Quality Improvements

### Reusable UI Infrastructure

The major architectural theme of v0.0.6 should be **reusable interactive terminal UI**.

Build shared primitives rather than feature-specific input loops where practical:

- Interactive list selector
- Interactive grid selector
- Detail panel/view
- Search/jump interaction
- Range/settings form
- Shared navigation footer/help

The existing `display_menu()` should remain the foundation for standard menus. fileciteturn13file0

### Separation of Concerns

Prefer this structure for new functionality:

`Data → Domain Logic → UI State → Terminal Renderer`

This is especially important for the Periodic Table so chemistry data is not coupled to ANSI/terminal layout code.

### Testing

Add/update tests for:

- Element lookup by symbol/name/atomic number
- Periodic-table layout mapping
- Element detail rendering data
- Electron configuration generation/data
- Interactive selection state transitions
- X min/max parsing and validation
- Y-range parsing and validation
- Graph generation across discontinuities
- Preset graph definitions
- Narrow-terminal / compact rendering where practical

Existing graphing and parser tests should be extended rather than replaced. fileciteturn7file8 fileciteturn4file8

## Definition of Done — v0.0.6

v0.0.6 is complete when **Periodic Table is a true interactive reference tool** rather than a paginated lookup, and **Graphing presents its coordinate/range controls clearly enough that a new user can immediately understand what X min/X max mean**.

The release should also establish the reusable interactive UI foundation that later Workstation CLI features can consume without duplicating navigation/rendering logic.
